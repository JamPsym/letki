System architecture
External USB-C PD charger -> VBUS -> custom V007 buck -> regulated 3.3 V
                                                       |-> display array
                                                       |-> X035 controller
                                                       `-> ESP-12F
PC -> USB data -> X035 -> UART/I2C -> display
Wi-Fi -> ESP-12F -> SPI (planned) -> X035
X035 -> I2C management -> V007
X035 -> CC1/CC2 -> charger PD negotiation

X035 dongle / communication board
Use CH32X035, not CH32X033, for integrated PD capability. From the display's
perspective the dongle is a computer/host speaking the same public protocol
as other hosts. X035 coordinates PC and Wi-Fi requests; ESP8266 is its Wi-Fi
peripheral, not an independent display-bus controller in this baseline.
X035 also negotiates the charger contract and supervises the converter.
The controller board operates from external regulated 3.3 V, supplied by the
buck in the integrated system or a separate development supply on the bench.
Do not inadvertently parallel those supplies.

PC USB is for data, not display power. Simultaneous PC data and charger input
require separate connection/power paths; connector choice, VBUS detection,
backfeed prevention and CC routing remain schematic work. The WeAct board is
a development aid, not a qualified high-current PD power path.

V007 converter board
Develop a custom buck power stage with V007 local regulation/control, sensing
and protection. Final asynchronous/synchronous topology, control-loop method,
gate driver, switching frequency, component ratings and compensation remain
learning/design decisions. The main regulator is not replaced by a ready-made
module merely to avoid converter design. Prototype at modest current using a
current-limited DC source and a test load before increasing power.

Output remains 3.3 V for v3.2 whether input is initial USB-C 5 V or a higher
negotiated PD voltage. The converter must start autonomously from 5 V before
X035 can negotiate. V007 therefore requires an input-derived startup/bias
supply independent of the initially absent main output; circuit remains TBD.
X035 boots on the resulting 3.3 V, negotiates PD, then permits higher load.
Keep startup consumption within available initial USB-C power; LED blanking
or load enable implementation remains TBD. Maintain output regulation through
PD input transitions and define behaviour on contract loss/input collapse.
No extra always-on controller converter is assumed in this architecture.

Power budget and distribution
Provisional charger class: approximately 60–65 W USB-C PD, possibly an
inexpensive Lenovo laptop charger. No exact charger/cable/profile selected or
purchased. Verify supported profiles and cable rating before final ratings.
At 60 W input and assumed 90% efficiency, 3.3 V output is about 16.4 A; this is
a planning calculation, not a qualified converter rating or measured efficiency.

Keep existing VCC/GND edge connections, including doubled connection wires.
The array is one continuous power rail powered by ONE converter. Additional
feeds may distribute the SAME converter output to reduce voltage drop.
Do not parallel independent converters or assume isolated power sections.
Array size is flexible within the finite converter, charger and distribution
limits. Wide copper/planes and doubled wires are useful existing features,
but actual voltage drop, heating and current capacity need verification.

X035 knows the permitted PD voltage/current contract. V007 telemetry reports
actual measured operation. Available input power, output power and consumption
are distinct; allow for conversion losses and controller/ESP consumption.
Use the lowest applicable charger, converter and distribution limit. Host-side
brightness/power limiting can supplement local converter protection; exact
policy and tile protocol support remain to be defined.

Converter management and PC testing
Use 3.3 V I2C with common ground: X035 controller, V007 target. Candidate
operations: read input/output voltage, output current, faults and temperature
if sensed; set enable and bounded limits/setpoints; clear eligible faults.
The normal display output stays 3.3 V; arbitrary voltage changes while attached
to tiles are not an operating mode. Final register/packet contract is TBD.
Regulation and fast protection remain local to V007, independent of polling,
PC connectivity, Wi-Fi or X035 reset. Define defaults and communication-loss
behaviour during circuit/firmware design.

PC -> USB -> X035 -> I2C -> V007 supports logging, controlled parameter changes
and converter tests. A suitable PC-to-I2C adapter can exercise the same
management interface independently. No test software is implemented here.

Display interfaces and wireless maintenance
Normal commands: PC/ESP -> X035 -> standard tile UART/I2C protocol.
Updates: Wi-Fi -> ESP -> SPI (planned) -> X035 -> I2C -> resident tile loader.
The user handles initial SWIO wiring/programming manually. Wireless updating
is a maintenance feature, not the main project objective. Retain local recovery.
The V006 loader in docs/v3_2-network-update.txt is a proposal, not implemented;
its flash budget does not automatically apply to V003-based boards.

The independently developed v3.2 protocol determines bus roles/timing. Do not
silently move the display-head clock role to X035 or introduce competing I2C
controllers. Prefer a separate converter-management bus if pin resources
permit; shared-bus addressing, ownership and scheduling remain open.
Audit F8U6 pin multiplexing for USB, PD, tile UART, ESP SPI and I2C/debug before
committing a schematic. Do not assume all hardware peripherals coexist on
this small package. Use bounded buffering and explicit command arbitration.

Existing v3 streaming evidence: 230400 baud demonstrated on five boards,
including GRAY4 at 18 fps. 460800 failed the PC-to-head zero-error criterion;
921600 is unqualified. 115200 is the default/recovery rate. Protocol proposals
include higher baud negotiation; v3.2 must establish its own achievable rates.
These results are not an X035 throughput qualification or a v3.2 speed ceiling.
See docs/general-firmware-hardware-20261017.txt and general-firmware-protocol.txt.

BMI160 combines three-axis acceleration and three-axis angular-rate sensing,
with I2C/SPI and a 1024-byte FIFO. Check the actual breakout's supply, pull-ups
and interface straps before wiring. Sensor sampling can run on a local
dongle-controlled sensor bus if pins permit; log sample sequence, acquisition
timestamp and six-axis values to PC or Wi-Fi, with explicit loss counters.

The current v3 head remains display-I2C controller: 100 kHz, seven-byte clock
beacons every 100 ms. A logger attached at the head edge observes that same
shared bus using passive inputs without ACKs or clock/data drive. Do not start
gyro polling as another controller on this bus. Lossless passive capture while
handling USB/UART/Wi-Fi is unqualified; investigate suitable capture hardware
or a spare X035 dedicated to capture. Decode timestamps, addresses, direction,
bytes, ACK/NACK and errors with bounded buffers and explicit overflow counts.
Keep telemetry/log records separate from display command packets. No v3
firmware change is needed for UART hosting or a passive external logger;
having the v3 head actively read a new sensor would require firmware work.

Electrical development notes
Budget the ESP's 3.3 V supply for Wi-Fi transients separately from LED load
steps; do not assume the WeAct onboard regulator can power the ESP. Preserve
ESP programming access/boot straps and prevent boot logs entering tile command
streams. Keep antenna clearance from copper, metal and converter switching
nodes. I2C pull-ups are to 3.3 V; bus capacitance, wiring and unpowered-device
behaviour require review. Exact GPIO assignments remain open.

Later media/TV host discussion — 2026-10-18

"last" does not mean development ends there. It is not the current hardware workstream. The near-term focus remains ESP8266 -> SPI -> X035
-> generic display interfaces. Keep desktop and future appliance hosts compatible.

The user owns a spare device described as a VASOUN M2S with Intel N5095. This is
the leading reuse candidate for the eventual media host, not a deployed or tested
Letki appliance. The matching published M2S is a mini-PC with external DC input;
the user's actual enclosure, RAM, ports, radio and installed OS remain unverified.

Windows or Android would require platform adaptation. No OS installation or
change was requested. Raspberry Pi Zero 2 W, Android/Google TV and Android-based
Fire TV were alternatives discussed; no purchase or platform port was authorized.

Proposed media host responsibilities: local video/audio playback, animation or
prepared-timeline playback, optional FFT and timestamped Wi-Fi delivery to ESP.
HDMI audio is the initial synchronization candidate; Bluetooth requires output
latency calibration. The Wi-Fi/SPI proxy and end-to-end timing remain unqualified.
Ordinary HDMI cannot power the host from the TV; retain a suitable power source.
No changes to the independent V007 converter or 3.3 V display rail are implied.
